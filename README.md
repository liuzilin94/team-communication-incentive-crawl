第 4 组 GitHub 成果提交操作指南（组员通用版）

一、先统一文件命名和目录

每位成员使用自己的姓名目录，每项文献使用“六位书目编号_题名”建立文件夹。编号和题名以小组书目表为依据，例如：

team-communication-incentive-crawl/
├── README.md

├── 成员姓名/

│   ├── README.md

│   └── 002470_云阳县乡土志/

│       ├── README.md

│       ├── metadata.json

│       ├── 目录结构说明.txt

│       ├── 卷首.txt

│       ├── 卷一.txt

│       ├── 卷二.txt

│       └── 原始资料/

│           └── 002470_云阳县乡土志.pdf

├── 其他成员姓名/

│   └── 六位编号_题名/

└── 协作记录/

    └── PR与合并索引表.md
    

上图只示范组织方式，实际有几卷就保存几卷。单篇文章、公文、碑文和文物介绍可使用 正文.txt 或实际篇名，不人为编造卷次。已经分好的章节保留实际章名。

命名统一按以下规则执行：

对象	规则或示例
书目文件夹	002470_云阳县乡土志
正文卷次	卷一.txt、卷二十八.txt，使用汉字数字
单篇材料	正文.txt，或实际篇名
原始 PDF	002470_云阳县乡土志.pdf
多册原始 PDF	002470_云阳县乡土志_上册.pdf，按实际册次命名
按阅读顺序保存的图片	002470_云阳县乡土志_001.jpg、_002.jpg
固定说明文件	README.md、metadata.json、目录结构说明.txt

题名去掉最外层《》，清除末尾空格。Windows 不允许出现在文件名中的符号应统一替换，但在元数据中保留原题名。正文 TXT 使用 UTF-8 无 BOM、LF 换行。

PDF 必须保存为真实的 .pdf 文件。大文件若只存于网盘，在 README 中填写链接、文件名及位置；不要把链接文件命名成“电子 PDF”。GitHub 应保留可直接查看的 TXT 和元数据，便于审核，压缩包可作补充。

二、每本书填写哪些说明

README.md 应写明题名、编号、来源网址、作者或责任者、出版社或版别、当前取得的内容范围、正文文件清单，以及需要复核的内容。没有查明的信息填写“未详”或“待核”，不要推测补齐。

metadata.json 至少包含以下字段。示例中的占位内容和数字必须根据实际结果替换：

{
  "id": "002470",
  "title": "云阳县乡土志",
  "volume_count": null,
  "text_file_count": null,
  "total_characters": null,
  "source_url": "填写实际来源网址",
  "source": "填写来源平台或馆藏",
  "author": null,
  "publisher": null,
  "edition": null,
  "crawled_by": "填写成员姓名",
  "crawl_date": null,
  "content_scope": "填写全文、节选或实际取得范围",
  "notes": []
}

“卷数”与“TXT 文件数”分别统计：序言、目录、参考文献可能各占一个 TXT，但不一定属于正文卷。未完成的统计使用 null，不要将默认数字当作实际结果。

三、每位成员建立本次提交分支

建议使用 GitHub Desktop 提交文件，GitHub 网页审核与合并。

1. 打开 GitHub Desktop，选中小组仓库。
2. 确认当前本地修改已经保存并妥善提交，再切换到 main。
3. 点击 Fetch origin；出现 Pull origin 时点击，取得最新主分支。
4. 点击 Current Branch → New Branch，以最新 main 为基础创建本次任务分支。
5. 点击 Publish branch 发布分支。

统一使用以下分支格式：

feature/批次-成员拼音

例如：

成员	本次分支命名示例
成员甲	feature/b01-chengyuanjia
成员乙	feature/b01-chengyuanyi
成员丙	feature/b01-chengyuanbing
成员丁	feature/b01-chengyuanding

第二批改为 b02，后续依次递增。原有成员分支可保留历史成果；新任务从最新 main 建立分支，便于把本次变化控制在明确范围内。

四、放入文件并提交

1. 在仓库本地目录中，整理本人姓名下的文件。
2. 已在 main 中存在的书目直接更新，避免再复制一份同名目录。
3. 回到 GitHub Desktop 的 Changes 页面，逐项查看新增、修改和删除文件。
4. 确认没有误删除他人成果，也没有带入临时文件或无关材料。
5. 在 Summary 填写清楚的提交说明。
6. 点击 Commit to 当前分支，再点击 Push origin。

提交说明示例：

整理：第一批书目目录与正文
修订：002470_云阳县乡土志卷次命名
补充：本批书目来源与版别信息

一次提交围绕一个明确任务组织。实际涉及多少书目、多少文件，就填写多少。

五、发起 PR

推送后，在 GitHub Desktop 点击 Preview Pull Request → Create Pull Request，或进入仓库网页选择 Pull requests → New pull request。

重点确认方向：

base：main
compare：本人本次任务分支

PR 标题统一为：

第一批书目整理与来源补充

正文使用以下通用模板；组长可将其保存为仓库中的 .github/pull_request_template.md，方便以后自动调用。

## 本次提交
- 提交人：
- 批次：
- 对应书目编号：
- 涉及书目数量：
- 主要处理内容：
- 来源及文件所在位置：

## 自查清单
- [ ] 编号和题名与书目表一致
- [ ] 按实际卷次或篇名组织 TXT
- [ ] TXT 可正常打开，编码和换行符合要求
- [ ] README、metadata 和目录说明齐全
- [ ] 元数据统计与实际文件一致
- [ ] 原始资料或其保存位置可以追溯
- [ ] 未误改、误删他人成果

## 当前范围与待核问题
- 已取得内容：
- 尚需复核内容：

## 请求审核
- 审核人：
- 建议重点检查的书目或文件：

完成自查的项目才勾选。尚未达到交付条件可先建 Draft PR；准备好后再转为可审核状态。

六、安排交叉审核

可采用轮流审核，使每个人都承担提交与检查两种角色。审核人进入 PR 的 Files changed，检查目录、文本及元数据，并对照原件抽查。至少写明检查了哪些书目或文件、发现了什么、结论是什么。

点击 Review changes 后选择：

1. Approve：检查通过。
2. Request changes：存在需要修订的问题。
3. Comment：提出说明或建议，暂不作通过结论。

最后点击 Submit review，正式提交审核。PR 作者不能批准自己的 PR。

审核意见可按此填写：

已检查【书目编号/文件范围】，核对了【目录、卷次、文字或来源信息】。
发现的问题为【实际问题】。
审核结论：【通过/修订后复核】。

如果没有发现问题，应写清楚实际检查范围，不把抽查表述为逐字核验全部内容。

七、修改问题并复核

提交人收到反馈后，在原 PR 对应的分支修改文件，重新 Commit → Push origin。后续提交会更新同一个 PR。

在 PR 回复中写明问题、修改位置及结果；审核人复核后再提交审核结论。已解决的讨论可标记为解决。这样，报告中就有“发现问题—整改—复核”的真实材料。

八、审核后合并到 main

由组长或具备权限的负责人操作：

1. 确认他人审核已经提交，必要问题已经处理。
2. 检查 PR 中最终文件差异及冲突提示。
3. 有冲突时先处理并复核，再合并。
4. 点击 Merge pull request → Confirm merge。若仓库采用其他合并方式，按统一约定执行。
5. 确认 PR 显示 Merged，并打开 main 检查文件确已进入目标位置。
6. 记录 PR 链接、合并时间及合并提交标识。

只有显示 Merged，才能在报告中写“该 PR 已合并”。组长自己的成果也应由其他成员审核。

九、发生冲突时怎样处理

若确有冲突，先比较双方修改及原始依据，再决定如何合并。TXT 应核对正文，元数据应核对来源表；涉及不同版本资料时，可保留区分说明。

处理完成后，提交修订、重新推送，请审核人检查，再合并。若本批没有冲突，记录“本批未出现合并冲突”，并介绍采用了成员独立目录、同步主分支、审核后合并等预防措施即可。

每位成员完成一轮有实际内容的提交、交叉审核和合并，就能够形成完整的协作案例。工作量评价同时考虑书目篇幅、资料难度、整理内容和审核任务，不能仅按 PR 数量判断。
